# 009 — Full-text search: generated `tsvector` columns + `ts_rank`

Status: Accepted

## Context

`TAPS-3.4` needs search across `Post` and `ExamBoard`, ranked by relevance, per `05-ARCHITECTURE.md`'s
"Postgres full-text search initially" choice (explicitly not Meilisearch). The Sprint 2 proposal
flagged the real trade-off directly: "a generated `tsvector` column + `GIN` index vs. a plain
`ILIKE` query." The acceptance criteria settles this itself — it requires results "ranked by
relevance (Postgres `tsvector`/`ts_rank`)," which a plain `ILIKE` substring match cannot do (no
relevance signal at all, and no usable index for arbitrary substring matching at scale).

## Decision

**Generated, `STORED` `tsvector` columns**, populated by Postgres itself on every write — not
maintained by application code, and not able to drift out of sync with `title`/`body` (`Post`) or
`name`/`description` (`ExamBoard`), because Postgres recomputes them as part of the same write.
`setweight('A' | 'B')` ranks title/name matches above body/description matches, so a keyword found
in a post's title outranks the same keyword only appearing in its body. A `GIN` index on each
column makes the `@@` match operator fast at any real content volume — the same benefit an `ILIKE`
scan can't offer, since `ILIKE '%term%'` can't use a standard btree index at all.

Prisma has no native `tsvector` type, so these columns are declared `Unsupported("tsvector")?` in
`schema.prisma` — present so the schema keeps accurately describing the real database shape (a
future migration diff won't think the column should be dropped), but never written to through
Prisma Client; only ever queried via `$queryRaw`. The migration itself
(`prisma/migrations/20260910215452_add_search_vectors`) is hand-written SQL, not generated by
`prisma migrate dev` — consistent with `docs/runbooks/database-migrations.md`'s note that command
refuses to run in this non-interactive environment; used `prisma migrate deploy` to apply it, same
as every migration in this repo since `TAPS-2.4`.

**Search combines both tables via `UNION ALL`** in `SearchService`
(`apps/api/src/public-content/search.service.ts`), using `websearch_to_tsquery` (not
`to_tsquery` or `plainto_tsquery`) specifically because it accepts arbitrary user input —
quotes, `OR`, `-excluded` terms — without ever throwing a syntax error the way `to_tsquery` would
on malformed input from a public search box. Only _published_ posts are searchable, matching the
public-read rule everywhere else (`docs/adr/006-public-content-api-shape.md`). Pagination reuses
the same `PaginationQueryDto`/`Paginated<T>` shape as every other public list endpoint.

Verified live against the real Neon database: `?q=delhi` correctly surfaces DSSSB; `?q=teacher
eligibility` ranks UPTET/HTET (both literally titled "Teacher Eligibility Test") above CTET; a
real published post is found and ranked highest for a direct keyword match, while a draft with a
matching keyword is correctly excluded; a query matching nothing returns `200` with an empty
array (not an error); a missing `q` returns `400` with a clear validation message. All
verification `Post` rows deleted afterward.

## Consequences

- **Easier:** relevance ranking that's actually meaningful (title matches outrank body matches);
  no manual reindexing step — the generated column is always correct; adding a third searchable
  model later is the same three-line pattern (generated column + `UNION ALL` branch).
- **Harder:** Postgres full-text search's linguistic features (stemming, stop words) are tied to
  the `'english'` text search configuration — fine for this product's English-language content now,
  would need reconsidering if/when Hindi content is added (`02-PRODUCT-VISION-AND-PRD.md`'s Phase 3
  localization). `UNION ALL` across two tables means the query planner can't use a single index
  scan the way a dedicated search index (Meilisearch, etc.) would — acceptable at current and
  near-term content volume; `05-ARCHITECTURE.md` already names Meilisearch as the fallback "if
  relevance becomes a problem."
